3. **Candidate verification flow.** Public applications return the same neutral receipt without exposing an application ID. Existing job/email combinations remain unique and can request another verification email. Legacy portal URLs show a generic email form; they disclose no candidate data. Requests require a matching application email and tenant, allow one send per minute and five per hour per application, and use the existing sensitive SMTP delivery path. Preview logging cannot activate a link. Failed delivery invalidates the reserved hash.

   Links contain a 256-bit random secret in the URL fragment, expire after 15 minutes and require an explicit confirmation POST, avoiding GET consumption by email scanners. The secret is removed from browser history before submission. An atomic conditional update consumes it once and creates a separate 256-bit browser credential. Both credentials are stored only as SHA-256 hashes. Production cookies use `__Host-`, HttpOnly, Secure, SameSite=Lax, Path=/ and a maximum effective lifetime of 24 hours. A fresh verification replaces the prior session. Resending invalidates the previous link. Access always checks application, tenant, expiry, persisted revocation and lifecycle; identifiers only select resources.

   The shared guard covers the portal page/metadata, exported data action, both candidate upload actions and both download/preview handlers. Upload updates also predicate on the current credential and lifecycle after storage work. The original resume handler remains staff-only. Staff cookies never fall back to candidate credentials. Rejection, withdrawal and onboarding completion permanently revoke credentials through the existing mutation transactions; live lifecycle predicates additionally deny terminal records. Hired candidates retain access while onboarding is incomplete. HR/Admin can revoke access or allow fresh verification; re-enabling does not restore an old cookie or link.
