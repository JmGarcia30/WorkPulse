## Delete/archive review and remaining limitations

1. Existing [payroll draft deletion](../../src/features/payroll/service.ts) already requires authorization, a locked DRAFT period and no generated entries or statutory inputs. It was preserved. Finalized payroll remains immutable. No bulk deletion or payroll cascade was added.
2. Existing [schedule archive/deletion](../../src/features/attendance/service.ts) scopes permissions/organization, blocks deletion of assigned versions/groups and retains immutable schedule history. Archive remains the existing alternative. These controls were inspected, not rewritten; this batch does not claim a new schedule-delete browser test or historical archive audit coverage.
3. The only new deletion is an unused, never-published recruitment job draft. Existing applications, hired employees, attendance, documents and immutable history are never deletion targets. Previously published drafts remain ineligible even if their status is later set back to DRAFT.
4. Duplicate recruitment submissions remain a review/archive workflow gap. A new submission deletion/archive design was intentionally not introduced: applications may own documents, stage history, offers, onboarding and employee conversion dependencies. The existing state/history safeguards and duplicate-operation protections remain. This is **P2, deferred**, not a claim that duplicate applicant submissions can now be erased.
5. Legacy HR accounts without matching activated invitation or verified company-registration proof cannot receive recovery links or security alerts. Employee recovery requires an activated, enabled account linked to an active employee. Missing verification is **account configuration/eligibility**, not a reason to email an unverified address or manufacture verification history. The existing authorized activation/verification process is required.
6. Security email delivery is **at most one SMTP attempt per recipient per lockout**, not mathematically exactly-once delivery. Durable claims prevent floods; a process crash after claim or an ambiguous SMTP failure can lose an alert. Claim/accepted/failed events expose that distinction to authorized system administrators. There is no new retry worker/outbox. Recovery similarly reserves its 15-minute issuance window even on delivery failure; public responses stay generic. A live delivery/operations rehearsal remains a release gate.
7. Audit Logs shows the newest **100 recorded events**, not an exhaustive searchable/exportable archive. It combines new security/job events with existing platform organization/invitation, employee account, attendance correction, finalized payroll, branding, RFID and application-status records. Old unrecorded profile/logins/job mutations/deletions are not backfilled. Standalone Platform Administrator sign-in/account-setting events and older schedule/payroll-draft deletions still lack this new event coverage. Their authentication mechanism was intentionally preserved.
8. The audit viewer contains no raw payload drill-down. Unknown legacy actions get a fixed generic label. It reports only recorded outcomes; it cannot reconstruct missing history. Existing finalized payroll metadata is read without amounts. Tenant HR does not get a centralized audit page.
9. No retention/purge policy for reset receipts, authentication budgets or immutable security history was added. Production retention/operational monitoring and any future reliable email retry design require separate review; immutable audits must not be purged casually.

## Migration and demonstration/release gates
